## Create Performance Task Requirements

Plan your own feature around these requirements. A full-stack framework,
database, login system, or deployed website does not automatically satisfy the
Create Performance Task.

| Requirement | Evidence in Your Program |
| --- | --- |
| **Program with Purpose** | Explain the problem or creative interest, intended audience, and useful functionality. |
| **Input** | Identify input from a user, device, online data stream, or file and show how the program uses it. |
| **Output** | Show output based on the input and the program's functionality. |
| **List or Other Collection** | Store and use multiple elements in a collection that manages complexity and supports the program's purpose. Explain what would be harder without it. |
| **Student-Developed Procedure** | Identify a procedure you developed, with one or more parameters that affect its functionality, that contributes to the program's purpose. |
| **Sequencing** | Show ordered steps in the algorithm inside that procedure. |
| **Selection** | Show a decision in that same procedure's algorithm. |
| **Iteration** | Show repetition in that same procedure's algorithm. |
| **Calling Procedures** | Show where your program calls the student-developed procedure, the arguments passed, and how its result or behavior is used. |
| **Testing and Errors** | Identify inputs and expected outputs or behaviors, compare actual results, and explain errors and corrections. |

The selected procedure's algorithm must contain **sequencing, selection, and
iteration together**. A built-in/library call, framework callback, or copied
starter code does not by itself establish student-developed procedural
abstraction. Follow the official rules on collaboration, attribution, and
permitted assistance; be ready to explain your own work.

### CPT Submission and Exam Evidence

| Component | What to Prepare |
| --- | --- |
| **Program Code** | Submit the complete program code and acknowledge contributions that are not your own as directed by College Board. |
| **Video** | Independently demonstrate input, at least one aspect of functionality, and output; follow the official format and privacy rules. |
| **Personalized Project Reference (PPR)** | Independently capture the required procedure definition and call, plus collection storage and use. Exclude comments from the PPR captures. |
| **Written Responses** | On the AP exam, explain program purpose/function, algorithm development, errors/testing, and data/procedural abstraction. These are not a separate written-reflection upload. |

## Project Goals

These are class project expectations supporting your CPT preparation, not
additional College Board submission requirements.

## Project Planning and Development Priorities

### Big Idea 1.1 & 1.2: Collaboration, Program Function, and Purpose

| Area | What to Practice |
| --- | --- |
| **Scrum, Agile, Issues, and Kanban** | Track tasks, iterations, responsibilities, and progress. Distinguish iterative project development from iteration in a program's algorithm. |
| **Program Code** | Explain how your own feature's code supports its purpose; use assigned practice questions to build understanding, not as a replacement for your program evidence. |
| **Personalized Project Reference** | Select the required code from your own program and explain its behavior. Practice questions are preparation, not the PPR itself. |
| **Tools and Methods** | Choose tools and methods that help achieve the program's purpose. |

### Big Idea 1.3: Program Design and Development

| Area | What to Practice |
| --- | --- |
| **Frontend/Backend Integration** | Build a usable interface and a backend that supports its functionality. |
| **Improvement** | Incorporate feedback from earlier work, including N@tM reviews. |
| **Design Documentation** | Use draw.io, UML diagrams, or flowcharts to explain the design. |
| **Code Quality** | Follow [PEP 8](https://peps.python.org/pep-0008/#introduction), use clear names, and document important logic. Source-code comments and attribution are separate from comment-free PPR captures. |

### Big Idea 1.4: Debugging Code and Fixing Errors

| Area | What to Practice |
| --- | --- |
| **Backend Debugging** | Send requests with VS Code REST Client and step through the Flask handler and model calls with the debugger. |
| **Frontend Debugging** | Use browser developer tools, including the Console and Network panels. |
| **End-to-End Tracing** | Follow frontend input through the request, API handler, data/model call, response, and displayed output. |
| **Testing** | Use authorized test data to check normal, boundary, and invalid inputs against expected results. REST Client requests are manual checks; automated tests need a runner with assertions. |

### Big Idea 2: Data

| Area | What to Practice |
| --- | --- |
| **Database Management** | Identify how the project stores data with SQLite and plan schemas that support the required features. Detailed model and SQL instruction belongs in a separate series. |
| **Security and Privacy** | Protect user data and consider privacy expectations and applicable rules. |
| **Retrieval and Display** | Trace queries and model results into frontend output; discuss efficient retrieval without assuming a database alone satisfies CPT collection requirements. |

### Big Idea 4: Internet

| Area | What to Practice |
| --- | --- |
| **HTTP and APIs** | Explain GET, POST, PUT, and DELETE requests and the contracts connecting frontend and backend. |
| **Authentication and HTTPS** | Use the application's existing authentication mechanism and HTTPS appropriately; distinguish authentication from authorization. |
| **Performance** | Consider asset size, caching, algorithm efficiency, and database access when investigating performance. |
| **Monitoring and Logging** | Use meaningful logs and monitoring to understand application behavior and failures. |
