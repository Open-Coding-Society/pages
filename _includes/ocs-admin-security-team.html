    What it does

    • Frontend password validationSignup blocks a password that fails the complexity rules and says what's missing. Invalid requests never leave the browser.
    • Spring password enforcementWeak passwords are rejected at the account-creation endpoint, so skipping the Pages frontend still yields no account.
    • Flask password enforcementThe same check runs on Flask's own account-creation route, so both backends apply the same rules.
    • GitHub and student ID check on signupBlocks signups that don't match.
    • Password resetA reset ticket is issued only after Google OAuth and GitHub ID verification. Tickets are rate-limited per IP, requests work without a signed-in session, and all active JWTs are invalidated when the password changes.
    • Safe password sync to FlaskPlaintext password sync is refused over non-loopback, non-TLS URIs.
    • Isolated Flask code runnerRequested Python runs in a dedicated code-runner Docker container. The main Flask container never executes submitted code.

    What's next

    • Isolated Spring code runnerA new Docker container runs submitted Java. The Spring API controller is being wired to send source code and request data to it and return the result.
    • Runner configurationMore Flask runner settings move into .env, so they change per environment without touching code.
    • Container hardeningCPU and memory limits, execution timeouts, filesystem and network restrictions, non-root execution, reduced Linux capabilities, and extra sandboxing. Every submitted program stays untrusted.
    • Spring API access controlPermissions on every endpoint, following the written plan.
    • Security log and audit systemA record of important security events.

    Our vision

    An OCS that anyone can safely join and grow in: open to students, teachers, and mentors, and locked down enough that no account, code, or data is left exposed.

    What we're working toward

    • Every account is verified and protected at every layer, from the signup form to both backends.
    • Student code always runs contained and never inside the main application.
    • The platform stays easy to maintain, with lean containers, safe migrations, and separate testing and production settings.
    • A mentor system gives new roles the right access, and nothing more.

    How we work together

    Focused sub-teams

    We split into groups for security, admin and database, and the mentor system, and each group owns its area from design to review.

    Daily meetings

    We meet every day to decide what gets done and to keep the shared board honest.

    One owner, a cap of two

    Every task has one named owner, and no one holds more than two at a time. Whoever has the least work claims first, so the load stays even.

    Reviewed and reported

    Changes move through review before they count as done, and every member adds to a weekly update each Thursday.
