OCS in a Kit

Everything that makes OCS ours becomes a setting, so another school can make it theirs.

Why this comes first: our security and backend work only reaches another school if it ships in a form that school can set up. So every feature we build keeps its school-specific values in the kit, not in the code.
Owned byThe whole team, alongside every feature

Security

Every kit ships safe: only verified people get in, and student code never touches the platform.

Owned byZhengji L, Harrish A, Jacob C, Lucas M
Built withSpring Boot Flask Docker JWT Google OAuth2

Shipped 5

✓Password rules at every layer. Checked in the frontend, Spring, and Flask, so skipping the website still yields no account.
✓Signup check. Blocks signups whose GitHub and student ID don't match.
✓Verified password reset. Needs Google and GitHub ID verification, is rate-limited, and signs out old tokens.
✓Safe password sync. Plaintext sync to Flask is refused over insecure links.
✓Isolated Flask runner. Python runs in its own Docker container, never in the main app.

In progress 1

  • Login cookies. Harrish is working on the cookies that keep a user signed in, so a session stays secure from login to logout.

Next 7

  • Simpler password policy. Spring's password-complexity check is causing support issues, so it comes out first.
  • Forced password reset. Anyone on a weak or default password must change it at login.
  • Yearly re-verification. Students confirm who they are at login once a year.
  • Isolated Spring runner. Java gets its own container. The API wiring is in progress.
  • Runner hardening. Settings move to .env, plus resource limits, timeouts, non-root execution, and restricted network and filesystem.
  • Spring access control. Permissions on every endpoint.
  • Audit log. A record of important security events.

Backend

Every kit ships runnable: each account has a known state, and staff can see and change it.

Owned byHarrish A, Arnav P, Darshan S, Shayan B, Rudra J, Dhyan S, Lucas M
Built withFlask Spring Security Google OAuth2 Database migrations Docker

Shipped 6

✓Account activation. Every account carries an active flag and a last-verified date (Flask #82, pages #1768).
✓Student activation. Students are activated by signing in with their school Google account.
✓Mentor verification. Signup can identify a mentor, and mentors start inactive until staff verify them.
✓Mentor role. ROLE_MENTOR sits between teacher and admin, with its own view of the site.
✓Support pages rework. A dropdown groups the support tabs, with guides for new students.
✓Docker cleanup. Redundant images and containers removed.

In review 3

  • Guest accounts. Keep them working under the new activation rules.
  • Backup restore. Restoring a backup keeps each account's activation state.
  • Pending status. A user who is waiting on verification can see their own status.

In progress 1

  • Mentor dashboard. We are building a dashboard where each mentor tracks only their own groups' progress and notes, building on the mentor role and verification already shipped. Darshan leads it, with Harrish building alongside.

Next 5

  • Account Administration screen. Teachers and admins see all accounts, filter by role and active status, and activate or deactivate. A prototype runs locally. Still open is whether a teacher may deactivate an admin.
  • Status column. Shows each account's state with a deactivate action. It waits on the kit's data file.
  • Production vs. testing config. Separate Spring settings, so test settings never reach production.
  • Spring database migration. Move the Spring data to the new setup, with upgrades applied automatically.
  • AI review with mentor design. Mentor-guided review of student work.
