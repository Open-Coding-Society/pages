2026–2027 · CSP · Two-week frontend sprint

Build a playable game by making one clear choice at a time.

We are extending UESL’s working Game Maker with a guided frontend path for participants who may find a full editor overwhelming. The engine, accessibility tools, and save system stay; the creation experience becomes calmer and clearer.

Open sprint plan View inherited project

Existing strengths and planned improvements

Inherited and working

UESL already has a drag-and-drop editor, Canvas game engine, accessibility settings, preview controls, and local/account saves.

Focused user problem

First-time participants can face too many technical choices at once, making it difficult to reach a confident first playable result.

Frontend sprint vision

Add a six-step guided mode that reuses the existing systems and keeps the advanced editor available for users who want it.

Scope boundaries

This sprint excludes multiplayer, AI generation, uploads, new accounts, public publishing, new backend systems, and rebuilding the inherited editor.

Two-week sprint plan

Week 1 · Prove the complete path

  1. Audit reuse points and approve the shared contract.
  2. Build three isolated first prototypes.
  3. Integrate Start → Accessibility → Preview.
  4. Capture teacher/peer feedback in a review ticket.

Week 2 · Revise, deploy, verify

  1. Correct weak interactions and contract gaps.
  2. Complete save/restore and preview recovery.
  3. Run mobile, keyboard, zoom, and boundary tests.
  4. Deploy, teammate-verify, demo, and reflect.

Kanban: Backlog → In progress → Code complete → Deployed → Verified.

One main task per person. Every PR links its issue, lists tests, receives a teammate review, and records the feedback-driven revision before verification.

Testing and portfolio evidence

Final demo path

Create a named game → apply a calm, high-contrast preset → override one setting → preview → save → refresh → restore.

Acceptance checks

  • Keyboard, visible focus, reduced motion, and 200% zoom.
  • Phone and desktop without clipping or page overflow.
  • Specific validation and safe corrupted-draft recovery.
  • Start, pause, reset, exit, save, and restore.

Collaboration history

Every work session adds an issue comment: Goal → Built → Evidence → Test result → Feedback → Next revision. Commits, teammate reviews, Kanban movement, and the correcting change preserve the iteration story.

Function and purpose

Inputs: game and accessibility choices. Events: navigate, validate, preview, save, restore. Outputs: feedback and configured gameplay. Data: one builder-state object and an accessibility-options list.

Evidence each teammate leaves behind

Individual issue and Kanban history · storyboard or prototype · meaningful commits and PR · review given and received · failed attempt plus correction · personal procedure/function · input/event/output/data explanation · repeatable tests · 1–2 minute live explanation.
