Capture & Processing Logic

Each capture cycle creates a timestamped observation. Jarvis preserves the original frame, processes it through YOLO and SAM 3, and compares the result with recent observations before changing the room model.

sequenceDiagram
    participant Cam as Classroom Cameras
    participant Cap as FFmpeg Capture
    participant AI as YOLO + SAM 3
    participant Track as Tracking Logic
    participant Room as Room Model

    loop At each configured interval
        Cam->>Cap: provide current frame
        Cap->>Cap: save original with camera ID + timestamp
        Cap->>AI: submit frame for inference
        AI->>Track: classes + confidence + boxes + masks
        Track->>Track: compare with recent observations
        Track->>Room: confirm new, moved, continuing, or missing objects
    end
    Note over Track: One weak or missed detection does not immediately change the room model
Object Observation State Model

Jarvis converts raw detections into stable states so that a single uncertain frame does not create a false report:

StateEvidenceMeaning
CANDIDATEOne new detectionPossible object awaiting confirmation from another frame or camera
CONFIRMEDRepeated compatible detectionsObject is accepted into the current room model
CONTINUINGClass and position remain compatibleThe same tracked object is still present
MOVEDSame object class and track, significantly different locationJarvis records a location-change event
UNCERTAINLow confidence or conflicting class predictionsObservation is saved but does not immediately overwrite a confirmed label
OCCLUDEDTemporarily missing from one view but supported by recent history or another cameraObject remains in the room model during a short evidence gap
MISSINGAbsent across enough consecutive observationsPreviously confirmed object is treated as removed or no longer visible
CAMERA_CONFLICTCamera observations cannot be matched consistentlyFlag for review instead of counting two views as two separate objects

Data the system needs to persist

This is the current entity list, not a final database schema.

  • Cameras — id, device name, host computer, viewpoint, resolution, status
  • Frames — id, camera, capture timestamp, original-file path, processing status
  • YOLO Classes — class id, object label, and training-version metadata
  • Detections — frame, class, confidence, bounding box, model version
  • Segmentation Masks — detection, mask-file path or encoded mask, SAM 3 model version
  • Object Tracks — persistent object id, current class, state, first seen, last seen
  • Locations / Zones — camera-relative coordinates and eventual room-relative position
  • Observations — track, frame, camera, position, confidence, mask, timestamp
  • Change Events — new, moved, missing, reappeared, or camera-conflict event
  • Model Runs — configuration, thresholds, processing time, errors, and output version
Design Decisions & Rationale
Design featureWhy
Use two cameras on opposite sides of the roomA second viewpoint reduces blind spots and gives Jarvis another observation when an object is blocked or unclear in one camera.
Capture timestamped still images instead of processing continuous 4K videoPeriodic frames reduce storage and CPU demand while preserving the time information needed to compare changes.
Begin at a 10-second capture intervalThis is frequent enough for initial room-change experiments and can be adjusted after measuring processing time and missed events.
Use YOLO for object recognition firstThe first version focuses on reliable object classes, bounding boxes, and confidence scores. Material recognition remains a later extension after the object pipeline works.
Start with six core classroom classesChair, table/desk, laptop, backpack, bottle, and book provide a manageable first dataset while testing fixed furniture, portable equipment, and small objects.
Use SAM 3 for segmentationSAM 3 supplies precise object masks, separating the pixels belonging to an object from its background; it does not replace the recognition model.
Defer material classificationMaterial labels such as wood, metal, plastic, glass, and fabric require separate training or classification work and are outside the first implementation milestone.
Use OpenCV for image handlingOpenCV can load frames, resize or normalize them, crop detected regions, draw results, compare frames, and save processed outputs.
Keep recognition confidence separate from tracking confidenceJarvis may be confident that an object persisted across frames even when its exact class is uncertain, or vice versa.
Require multiple observations before declaring a changeA single missed detection should not immediately cause Jarvis to report that an object disappeared or moved.
Use an 80% first-prototype success thresholdJarvis must correctly classify at least 80% of objects and correctly determine at least 80% of tested object states on held-out, manually labeled scenes.
Process on a main Linux computerCentral processing keeps the room model and saved results together while a second Linux computer can capture and transfer images from the remote camera.
Privacy, Scope & Governance

Jarvis is designed to understand classroom objects, not identify or monitor individual people:

DecisionDetail
No identity recognitionJarvis does not use face recognition, names, student IDs, biometric enrollment, or any other method to determine who a person is.
Generic person detection onlyA person may be represented only as the class person, allowing Jarvis to recognize that a classroom object may be temporarily blocked from view.
No persistent person trackingPerson detections are not assigned lasting identities and are not included in the classroom object inventory or movement history.
Object-focused outputsSaved detections, masks, and change events focus on classroom objects; people are treated as temporary occluders rather than subjects of analysis.
Local prototype scopeThe first version runs on the project's Linux computers for testing in the selected classroom rather than serving as a school-wide surveillance system.
Controlled evaluationInitial accuracy testing should use team-controlled scenes and objects, with classroom testing conducted only under the permission rules established for the project.
A generic person mask may explain why a previously confirmed object is temporarily invisible. In that case, Jarvis should prefer OCCLUDED over immediately changing the object to MISSING.
